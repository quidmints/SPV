## 1. What was changed

### §AUDIT-PUSHOBS — `Core.pushObservation` is now ETH-instance only
`src/Core.sol` — one guard plus its reasoning.

The finding is right, **but the gate named in SPRINT (`observationSource != 0`) is the wrong gate
and would have made the situation worse.** Evidence, gathered before writing anything:

* `setObservationSource` has **no production caller**. `DeployLib.sol:139` explicitly declines to
  pin a source ("§E222 — NO OBSERVATION SOURCE IS PINNED"), and the only caller in the tree is
  `test/DrainAtomicity.t.sol:1375`. So `observationSource == address(0)` on **both** instances.
* `pushObservation` is therefore the ring's **only live writer** — that is §E294/§E308's whole
  point ("σ² ≡ 0 because the ring has two writers and neither runs"). Gating on the pull source
  would refuse every push on ETH as well and deepen the finding it was meant to close.
* It would also go red in `LevCascade`, `LevYbReal`, `LeverageCrossSubsidyProbe`,
  `PushObservationFillsTheRing` and `Alles`'s ramp helpers, all of which push into a `Core` with no
  source pinned. That would be the CHANGE being wrong, not the tests being stale (rule 8d).

⇒ The gate landed as **instance identity**: `if (VOL_DECIMALS != 18) return;`. That is the same
derivation the function already used one line below to compute `isWbtc`, so it is free and local.
The `isWbtc` argument to `twapResolve` is now the literal `false`, because after the gate the
expression is provably false and provably-false code is not allowed to stand.

Why the bug matters, stated in the code and repeated here because it is **not** the usual oracle
attack: the 50 bps bound stops a pusher moving the LEVEL. It does nothing against a pusher who
submits a stream of *in-range* values at the BTC `Core`. That fills the ring, makes σ²
small-but-MEASURED, and so **replaces §E213's ceiling sentinel with a near-floor number** — an
attacker buys a cheap BTC skew by being helpful, and nothing reverts.

Rejected alternative (recorded because it is the "proper" fix and someone will propose it): carry
an explicit per-instance flag on the risk profile (`SwapLib.Risk`, `SwapLib.ethRisk/btcRisk`,
`ICore.riskParams`). That is the honest home for deploy-time configuration and matches
`Core.sol:567`'s warning against inferring the profile from decimals. It was **not** taken here:
`Risk` is a 2-field struct whose own docblock (`SwapLib.sol:810`) records that it exists *because
`sellSkew` sits exactly at the legacy stack limit with two measured stack-too-deep incidents*, and
widening it also changes `riskParams()`'s ABI. That is a build-and-measure change, and this lane
could not build. The decimals gate is the assumption-free half.

### §AUDIT-DELIVER-KEYS — `deliverSwapOutOnchain` now pins the channel keys
`src/BTCChannels.sol` — `_requireChannelKeys(channelId, p);` added to the outer frame, next to
`_onlyHop()`.

`_deliverSwapOut` rotates the funding outpoint and proves the rotation with `_verifySplice`, which
`splice:1123` states outright "proves KeyAgg over **whatever pair it is given**". Without the pin a
compromised hop names its own pair and custody moves to a 2-of-2 the LP is not half of — verbatim
the attack `_requireChannelKeys`'s docblock (`:1832`) describes. Second-order and just as bad:
`keysHash` is left stale against a rotated outpoint, which is §E153's *unretirable forever*
regression (`:1258`).

Placement is deliberate: the **outer** frame, with `_armLadder`, because `_deliverSwapOut`'s note
records that extending any calldata live-range across its settlement tail overflowed the legacy
stack and reverted four tests. `p` is already live in the outer frame (it is passed to both
`_deliverSwapOut` and `_armLadder`), so this reads nothing new.

Call sites checked before writing — both build `p` from the channel's registered pair, so both
should stay green:
* `test/BtcLpMintStress.t.sol:770-789` — `lpPubkey: s.lpPubkey, hopPubkey: _hopKeyOf[s.channelId]`.
* `test/VBtcLevFeeLane.t.sol:1014-1032` — `hopKey_` from `ownedChannelKeys(_label(seed))`, with the
  comment "(E162) A delivery is a splice — same pinned pair as the channel."

### §AUDIT-SPV-RETARGET — unaligned checkpoint heights are refused
`src/spv/SPVGateway.sol` — new `error UnalignedCheckpointHeight(uint64)` (declared on the contract,
not on the vendored `ISPVGateway`) and `require(blockHeight_ % DIFFICULTY_ADJUSTMENT_INTERVAL == 0)`
in `__SPVGateway_init`.

`_getEpochPassedTime(h)` reads `getBlockHash(h - 2016)`. Init at unaligned H and the first retarget
above it needs a block **below** H: `getBlockHash` returns zero, the epoch-start time reads 0, the
recomputed target is garbage, every subsequent header fails `InvalidTarget`, and `initializer`
means there is no second chance. A routine difficulty adjustment bricks the BTC path permanently,
up to ~2 weeks after deploy.

New test: **`test/SPVGatewayInitAlignment.t.sol`** — three unaligned heights refused with the exact
selector, plus two controls (aligned signet 304416 accepted; genesis height 0 still initialises).
The controls are load-bearing: a guard that refused everything would pass the negative test alone.

Why the suite was blind: every gateway in the tree inits at height 0 (regtest/synthetic genesis:
`Alles.t.sol:243`, `OpenChannelE2E.t.sol:50`, `BtcSelfManaged.t.sol:333`,
`SPVGatewayAdversarial.t.sol:89`, `DriverE2E.s.sol:112`) or at signet 304416 = 2016×151
(`SPVGateway.t.sol:17`). Both aligned — by fixture habit, not by rule. Production takes the height
from an operator env var (`DeployL1_s.sol:328`), which is where the rule is needed.

This is a **sibling** of `DeployLib.sol:289`'s burial check, not a duplicate: that one asserts the
checkpoint is CANONICAL, this one that it is USABLE by the retarget arithmetic. A buried-but-
unaligned checkpoint passes that one and still bricks — which is why the check is on the gateway,
where a test or a deployer that never goes through `DeployLib` must also pass it.

### §AUDIT-OPENLPS-DOS — the open-position book is bounded (a clamp, deliberately)
`src/imports/RangeLib.sol` — `MAX_OPEN_LPS = 128`, `error BookFull()`, and `_requireRoom()` on
**both** writers (`trackOpen` and `openPos`; a cap on one of two writers is not a cap).
`src/imports/SwapLib.sol` — a note at `deleverEthOnDelivery` recording where its outer bound now
comes from, and instructing against adding a second clamp there.

**The bound cannot go on the loops, and that is the whole argument.** Truncating `totalNetEquity`
or `totalDeliverableDollars` at N would not bound a cost — it would return a wrong, smaller number
for the book's equity and deliverable dollars, silently, on the backing math. A gas clamp that
under-reports backing is worse than the DoS it prevents. The only place a bound is both effective
and truthful is the write that makes the loops longer.

It trades one denial for a smaller one, and that is stated in the code: at the cap a new LP cannot
open until someone closes (reachable by an attacker for ~128 × `MIN_OPEN_WEETH` ≈ 6.4 weETH of
real, at-risk collateral). Without the cap the same spend, continued, buys "no deposits, no
withdrawals, no swaps, for anyone, permanently".

⛔ **This is a clamp under CLAUDE.md rule 17 and it is meant to be deleted.** SPRINT item #1 retires
this class at the root by pooling venue positions and holding per-LP shares; when that lands there
is no book to walk, and `_openLps`, `_lpIdx`, `trackOpen`, `untrackOpen`, the four Σ-loops and this
cap all go with it. **A later root fix should delete this, not tune it.**

## 3. The variable-reduction question

### `netIssuanceUsd` (Aux:1328) vs `netFlowUsd` (Core:1280) — **CANNOT BE FOLDED**

The docblock at `Aux.sol:1295-1327` is **right**, and it is stronger than it claims. Five
independent obstacles, any one of which is fatal:

1. **Different decimal bases.** `netIssuanceUsd` is 18-dec (both legs are natively 18-dec basket
   shares: the redeem leg burns 18-dec QU!D at `Aux.sol:898`, the mint leg is lifted through
   `BasketLib.scaleTokenAmount(usd, token, true)` at `Aux.sol:1147`). `netFlowUsd` is 6-dec,
   mirroring the 6-dec `usdLeg` of a swap delta.
2. **Different cardinality, which is the obstacle the docblock understates.** `netFlowUsd` lives on
   `Core`, and **`Core` is two instances** (ETH + BTC — `DeployLib.sol:136-137`). `netIssuanceUsd`
   lives on `Aux`, of which there is one. A single global slot cannot carry per-instance travel and
   two per-instance slots cannot carry a global counter. There is no fold that is merely a rename.
3. **Disjoint writers, verified.** `netIssuanceUsd` is written at exactly two sites, both gated on
   the primary market (`Aux.sol:898` redeem; `Aux.sol:1147` under `msg.sender == address(QUID)`).
   `netFlowUsd` is written only via `Core._bumpFlow`, whose sole call site is inside `Core.swap`.
4. **A live test already asserts they are separable.** `test/NetIssuance.t.sol:82-86` fails if a
   mint or redeem moves `Core.netFlowUsd`, and `:104-106` fails if a swap moves
   `AUX.netIssuanceUsd`. Both assertions were written *as controls* for exactly this question. A
   fold cannot be landed without deleting them, and deleting a control to permit a fold is the
   loosening CLAUDE.md rule 8d forbids.
5. **`netFlowUsd` cannot even be MOVED, let alone merged.** Its own declaration note (`Core.sol`,
   "DECLARED LAST ON PURPOSE") records that `DrainAtomicity._flowTs` reads Core slots 262/263 by
   RAW INDEX and that a stale slot does not fail the test — `vm.load` silently reads the wrong
   variable and the test passes while measuring something else.

⇒ **Answer to the owner: no fold. They are the primary and secondary market registers of the same
paper (Lyons & Viswanath-Natraj, SSRN 3508006) and the model needs both distinct.** The variable
count is 2 because the quantities are 2.

### `forVolatile` (`Aux.swap/swapTo`, `SwapLib.SwapReq`, `ISwap`) — **CANNOT BE FOLDED**

Tested against the "always derivable from another param" hypothesis and it fails outright: the same
`(token, asset)` pair is legal in both directions. `test/SignedNetFlow.t.sol:77`
(`swap(USDC, WETH, false)` = SELL) and `test/Alles.t.sol:1561` (`swap(USDC, WETH, true)` = BUY) are
the same two addresses with opposite meanings, so the direction is genuinely independent
information and cannot be recovered from `token`/`asset`. There is no per-file duplicate either —
it is declared once in `SwapLib.SwapReq` and once in the canonical `ISwap` in
`src/imports/Interfaces.sol`, which is where the rule says it belongs.

Adjacent observation, reported not landed: `SwapReq.inToken` **is** derived
(`SwapLib.sol:349`, from `forVolatile`/`token`/`asset`). It is not a duplicate — the `forVolatile`
branch downstream zeroes `r.token`, so the derivation is not repeatable later and the field is a
memo of a value that no longer exists. Leave it.

### Sweep along the same seams

* **Per-file interface variants — already done, nothing left.** `src/imports/Interfaces.sol` is the
  single declaration site and its own comments record the unions already performed (`IAaveV4Spoke`,
  `IWeETH`, `IDepositAdapter`, `IAaveV4Hub`, `ILevVenueColl`, `ICollection`, `IAggregatorV3`, and
  three ERC-20 slices collapsed to `IERC20Min`). The only interface declared elsewhere in `src/` is
  `ISPVGateway`, which is vendored. **No action.**
* **Candidate, NOT landed: the four Σ-loops in `LevBase`.** `totalDeliverableDollars` (:231),
  `totalDebtUsd` (:431), `totalGrossCollateral` (:473) and `totalNetEquity` (:479) are the same
  walk over `_openLps` with a different per-LP accessor; two of them also read the oracle once up
  front. They are inherited by BOTH managers, so a single `_sumOver(...)` taking an internal
  function pointer would pay twice. **Refused for now:** a function-pointer fold changes codegen in
  a way that can go either direction on size, and the seam's own header
  (`RangeLib.sol:398-412`) records the hard limit — a library body cannot read the caller's
  immutables (`AUX`, `ORACLE_KEY`), so the oracle read must stay in the caller and the two
  price-taking loops do not have the same shape as the two that do not. This is a
  build-and-measure change and this lane could not build. It is also **partly moot**: SPRINT #1's
  pooling redesign deletes all four.
* **Candidate, NOT landed: `SwapLib.Risk` gaining the observation-policy flag** — see
  §AUDIT-PUSHOBS above. Would *raise* the variable count by one while deleting an inference; worth
  doing only together with a `riskParams()` ABI change and a measurement.

## 6. Static verification actually performed (in lieu of a build)

No compiler was available, so each risk that a build would have caught was checked by hand against
the tree. What was checked and what it found:

* **`require(cond, CustomError())` under solc 0.8.30 + `via_ir = false`** — supported, and proven in
  *this* tree, not from the changelog: `SPVGateway` already ships
  `require(blockExists(...), PrevBlockDoesNotExist(...))` and the repo has current build artifacts.
* **`Contract.Error.selector` in a test** — same pattern already in use at
  `test/VBtcLevFeeLane.t.sol:730` (`vm.expectRevert(LevBase.BadTarget.selector)`).
* **`TargetsHelper.DIFFICULTY_ADJUSTMENT_INTERVAL` visible in `SPVGateway`** — imported at line 12
  and already dereferenced identically at `SPVGateway.sol:464`. No name collision:
  `UnalignedCheckpointHeight` does not exist anywhere else.
* **`VOL_DECIMALS` in scope at `pushObservation`** — `Core.sol` declares exactly one contract
  (`contract Core {` at :46) and `VOL_DECIMALS` is its immutable at :401.
* **No test pushes to the BTC `Core`** — this is the regression that fix 1 could have caused. Every
  `pushObservation` call site in `test/` goes through `CORE`, which `Alles.t.sol:673` binds to
  `A.core` (the WETH instance; the BTC one is the separate `A.btcCore`), and every one of them pairs
  the push with `_setLiveEthFeed` / `assetPriceFeed(WETH)`. **Zero call sites hit the gate.**
* **No test can hit `MAX_OPEN_LPS`** — the lev fixtures use a handful of LPs (`LevCascade`'s
  `lps[0..3]`, `VBtcLevFeeLane` one at a time, asserting `openLevCount() == 1`). Nothing approaches
  128, so the cap is unreachable from the suite.
* **`RangeLib` collisions** — `MAX_OPEN_LPS`, `BookFull`, `_requireRoom` each appear only at their
  new definition and their intended uses; both push sites are capped.
* **`deliverSwapOutOnchain` call sites** — both build `p` from the channel's registered pair
  (`BtcLpMintStress.t.sol:770-789`, `VBtcLevFeeLane.t.sol:1014-1032`), so the new pin should pass.
* **Test-file hazard removed** — the negative case originally used a `uint64[3]` array literal,
  whose element-type inference is the kind of thing only a compiler settles. Rewritten as three
  calls to a `_expectRefused(uint64)` helper that also deploys a fresh gateway per case, so a
  one-shot `initializer` cannot make cases 2 and 3 pass on the wrong revert.

**This is not a substitute for the build.** It removes the failure modes I could see; it cannot
speak for `BTCChannels`'s bytecode headroom or for anything only the optimizer knows.
