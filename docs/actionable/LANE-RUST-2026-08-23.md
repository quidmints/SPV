## 1. §AUDIT-JUSTICE-WEIGHT (🔴) — fixed, test added

**Confirmed the defect exactly as filed.**

`chain/package.rs` used one unconditional constant for the revoked `to_local` justice
witness:

```rust
// number_of_witness_elements + sig_length + revocation_sig + true_length + op_true
// + witness_script_length + witness_script
pub(crate) const WEIGHT_REVOKED_OUTPUT: u64 = 1 + 1 + 73 + 1 + 1 + 1 + 77; // = 155
```

…and `RevokedOutput::build` assigned it with no `supports_simple_taproot()` branch, even
though `RevokedOutput::finalize_input` (package.rs ~1059) takes a **BIP341 script path**
through the revoke tapleaf on a taproot channel.

### Arithmetic (assumption-free — traced to the builders)

Witness is `[schnorr_sig, revoke_leaf, control_block]`
(`chan_utils::build_taproot_script_path_witness`).

| element | bytes | source |
|---|---|---|
| `number_of_witness_elements` | 1 | compact-size, 3 elements |
| sig len + sig | 1 + 64 | `taproot_schnorr_witness_element`, `SIGHASH_DEFAULT` ⇒ no type byte |
| leaf len + leaf | 1 + 68 | `get_taproot_to_local_revoke_script` = `push32 (33) + OP_DROP (1) + push32 (33) + OP_CHECKSIG (1)` |
| cb len + control block | 1 + 65 | `taproot_to_local_spend_info` → `taproot_spend_info_two_leaves` ⇒ *"depth 1 for each of two leaves"* ⇒ `33 + 32*1` |
| **total** | **201** | |

`201 > 155`, an **under**-estimate of 46 WU ⇒ `onchaintx.rs:636`
`assert!(predicted_weight >= transaction.0.weight().to_wu())` fires in release ⇒ the justice
transaction **panics instead of broadcasting**, on the breach-remedy path. Filing confirmed.

### The change

`lib/rust-lightning/lightning/src/chain/package.rs`

- Added `WEIGHT_REVOKED_OUTPUT_TAPROOT = 1 + 1 + 64 + 1 + 68 + 1 + 65` (= 201) with the
  full derivation and the panic consequence in the doc comment.
- Added `weight_revoked_output(&ChannelTypeFeatures) -> u64`, branching on
  `supports_simple_taproot()`.
- `RevokedOutput::build` now calls it instead of hard-coding the legacy constant.
- Left `WEIGHT_REVOKED_OUTPUT` in place — it is still the correct legacy value and is
  referenced from `chan_utils.rs` and the `channelmonitor.rs` tests.

### Tests added (this is why it survived — there were none)

1. `test_package_weight` — new block asserting a `dumb_taproot_revk_output!()` package
   predicts `weight_sans_output + WEIGHT_REVOKED_OUTPUT_TAPROOT`. New helpers
   `simple_taproot_channel_type()` (mirrors `channel.rs:15465` — `only_static_remote_key`
   + `simple_taproot_required` + `anchors_zero_fee_htlc_tx_required`) and
   `dumb_taproot_revk_output!`.
2. **`test_taproot_revoked_output_weight_matches_real_witness`** — the load-bearing one.
   Builds the *actual* leaf + `TaprootSpendInfo` `finalize_input` uses, assembles the real
   witness via `build_taproot_script_path_witness`, and asserts
   `witness.size() == WEIGHT_REVOKED_OUTPUT_TAPROOT` — i.e. the constant is pinned to
   measured bytes, not to my arithmetic. It also asserts the legacy constant is strictly
   less, which is the regression the audit found.

`quid-ln/tests/taproot_onchain_resolution.rs::justice_to_local_revoke_taproot` already
asserted the witness *shape* (`[sig(64), leaf, control_block]`) but never compared it to the
predicted package weight. That is precisely the seam the bug slipped through.

## 2. §C2.3② — THE ANSWER: **both topologies are real; the discriminator is `vault: Option<Arc<VaultNode>>`**

Traced from the code, not from either comment.

### Evidence chain

1. **`quid-bridge/src/bin/quid-bridge-daemon.rs:360`**
   ```rust
   let cohost_vault: bool = env_parse("QUID_FLEET_COHOSTS_VAULT", false)?;
   let vault = if cohost_vault {
       tracing::warn!("QUID_FLEET_COHOSTS_VAULT=true: this fleet holds BOTH halves of every
                       2-of-2. The multisig is nominal in this deployment (M1#2).");
       let vault_seed = quid_bridge::vault::derive_vault_seed(&root_seed);
       ... Some(vault)
   } else {
       tracing::info!("vault NOT co-hosted (M1#2): the LP half lives on the LP's own host ...
                       This fleet cannot unilaterally spend a channel's funding output.");
       None
   };
   ```
   **Default is `false`.** In the default the fleet has no vault node and no vault seed.
   In the opt-in the vault seed is `derive_vault_seed(&root_seed)` — a pure function of the
   *same* enclave root seed as the hop — so the fleet genuinely derives **both** halves.

2. **`quid-bridge/src/deadman_exit.rs:269`** — `run_deadman_exit_heartbeat` early-returns on
   `let Some(vault) = vault else { info!("...DISABLED — no vault node in this process..."); return; }`.
   This is the **only** place the fleet arms both signers; with `None` it never runs, and
   exits come from the §E165 LP-pre-signed ladder instead.

3. **`quid-bridge/src/deadman_exit.rs:150-164`** — under `Some`, it arms
   `vault_signer` from `vault.node.keys_manager` and `hop_signer` from `hop_keys` in one
   process and calls `quid_ln::deadman_exit::presign_deadman_exit(&hop_signer, &vault_signer, …)`.

4. **A premise test already guards the split** (`quid-bridge/src/deadman_exit.rs:565-577`):
   it greps its own source for `"vault: Option<Arc<VaultNode>>"` and
   `"let Some(vault) = vault else"` and panics if either disappears.

5. **Everything on `VaultNode` is co-hosted-only.** `VaultNode::deliver_swap_out`
   (`vault.rs:670`) and `run_swap_out_onchain_watcher` (`swap_out_onchain.rs:366`, takes a
   **non-optional** `Arc<VaultNode>`) only exist when `vault.is_some()`.

- `vault.rs:~244` said *"which after §E175 the fleet does not have"* — true for the

- Three other sites still asserted the **opposite** absolute (*"the fleet holds BOTH key

## 3. §AUDIT-TCB-CRL (🟠) — comment narrowed to what is actually true; check NOT implemented

**Both halves of the filing confirmed.**

`quid-tls/src/attest_client/verifier.rs`:

- `verify_pck_cert_chain` passes `let revocation = None;` to
  `EndEntityCert::verify_for_usage` ⇒ **a revoked PCK cert validates** as long as it chains
  to the pinned Intel SGX root CA and is in its validity window.
- There is no `cpusvn` / `fmspc` / `pcesvn` parsing and no TCB Info fetch anywhere in the
  crate.
- The note above `EnclavePolicy` claimed MRENCLAVE-pinning made SVN gating unnecessary.
  That claim is **half true**, and the false half is the dangerous one.

### Why the old comment was wrong

- ✅ **True for `isvsvn` / `isvprodid`** — both are properties of the *enclave binary*. A
  downgraded or wrong-product enclave is different code ⇒ different MRENCLAVE ⇒ already
  rejected by `EnclavePolicy::verify`.
- 🔴 **False for `cpusvn`** — `cpusvn` is a property of the **host** (CPU microcode + SGX
  PSW/QE TCB level). The *same* MRENCLAVE runs unchanged on a platform whose microcode is
  vulnerable and later revoked by an Intel TCB Recovery. The measurement check cannot see it.
- 🔴 **False for PCK revocation** — orthogonal to measurement entirely.

### What I changed

Comment only (two sites), stating exactly what holds:

1. The note above `EnclavePolicy` now splits ✅ COVERED (`isvsvn`/`isvprodid`, with the
   MRSIGNER-only caveat retained) from 🔴 NOT COVERED, and names the concrete missing
   mechanism for each: signed **TCB Info** for the PCK's `fmspc`
   (`.../sgx/certification/v4/tcb?fmspc=…`) matched against the PCK cert's SGX extension
   (`fmspc`, `pcesvn`, the 16 `cpusvn` components) and the quote's `cpusvn`, rejecting
   `tcbStatus` `Revoked`/`OutOfDate`; and the Intel PCK CRLs (root CA CRL +
   `platform`/`processor` CA CRL) as `webpki::RevocationOptions`.
   It closes with: *"DO NOT claim this verifier detects a revoked platform or a stale
   platform TCB: it does not."*
2. A 🔴 marker on the `let revocation = None;` line itself, so a reader lands on the truth
   at the call site rather than three hundred lines away.

### Not implemented — and why

A real gate needs **fetching + caching signed Intel PCS collateral** (TCB Info JSON + its
signing cert chain + two CRLs) plus a **freshness policy** for it. `verify_quote` is today a
pure in-enclave function over quote bytes with no I/O, no clock beyond the passed-in `now`,
and no collateral store. Bolting a network fetch into it would be the larger and riskier
change; the honest interim is an accurate comment. **This row stays OPEN.**

**Remaining work, precisely:**
1. Plumb a `Collateral { tcb_info, tcb_signing_chain, root_crl, pck_crl }` argument into
   `verify_quote` / `verify_pck_cert_chain` (fetched + cached outside the enclave, verified
   inside against the pinned root).
2. Build `webpki::RevocationOptions` from the two CRLs and pass it as `revocation`.
3. Parse the PCK cert's SGX extension OID for `fmspc` / `pcesvn` / `cpusvn[16]`, select the
   matching TCB level from TCB Info, and gate on `tcbStatus` per `DeployEnv`
   (`UpToDate` only in prod; allow `SWHardeningNeeded`/`ConfigurationNeeded` behind policy).
4. Tests: a revoked-PCK fixture must FAIL, and an out-of-date-`cpusvn` quote must FAIL.
